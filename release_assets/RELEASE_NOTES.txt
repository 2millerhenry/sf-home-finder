SF Home Finder 0.5.6

Checks finish about forty seconds sooner again -- measured across this
board's last thirty-seven checks, where the saving ran from half a minute to
just over a minute depending on how much each site had to say.

Version 0.5.4 began reading Craigslist alongside the rest of a check instead
of ahead of it, because Craigslist answers for itself: no other site sees its
requests. That is true of most of the sites here. Zillow, Trulia and HotPads
are one company and count our requests together; Rent.com, ApartmentGuide and
Apartments.com are another. The rest -- the city's own portal, Zumper, Uloop,
AvalonBay, SpareRoom, Movoto, Apartment List, UDR and the building managers --
each answer only for themselves.

So a check now reads those two companies strictly in turn on one line, and
everything that answers for itself on a second line beside it. No site is ever
asked for two things at once, and none is read faster than before: every one
still gets one page at a time, at the same pace, in the same order as its
neighbours on its own line. Each source declares whose limiter it answers to,
and a test refuses to let one company's sites be split across the two lines.

If this ever turns out to cost something, SF_HOUSING_SEQUENTIAL_SCAN=1 still
puts every source back in one line exactly as it was.

The homefinder command is also findable now, wherever you type it. It lives in
~/.local/bin, which a stock Mac shell does not search, and 0.5.5 added the
missing line to one file -- the one your shell reads when it opens a window.
That left it missing from the others: a zsh script reads a different file, so
does a login bash, and fish reads none of them and does not understand their
syntax. The line now goes into each file your own shell reads, once, written
in the syntax that shell speaks. Then the installer starts a fresh shell and
asks it whether the command is there, instead of telling you it will be, and
says so plainly either way -- including when some other homefinder earlier on
your PATH would answer first. Repair does the same, for anybody who would
rather double-click than type.

SF Home Finder 0.5.5

Three things, all of them from watching somebody install this on their own Mac
for the first time.

The homefinder command now works in the window you installed from. The
installer adds a line to your shell profile so that new terminal windows can
find it, but the window you are already looking at read that file when it
opened, so typing homefinder there said "command not found". It now shows the
two ways that work immediately, in the window you are in.

Near matches means near. It used to hold every home that was not on the
shortlist, which on a real board meant 7,785 homes -- 7,625 of which the deal
had ruled out outright, for the wrong number of bedrooms or twice the budget.
It now holds only homes that came within ten points of your cut-off: 127
rather than 7,785 on that same board, so the list is worth opening again.
Nothing is hidden; everything collected is still in the full archive.

Installing downloads about six megabytes less and installs ten fewer packages.
The app was asking for a bundle of extras it never used: a file watcher for
reloading code as you edit it, a websocket library, and two speed-ups meant
for servers with more than one user.

SF Home Finder 0.5.4

Checking for new homes takes less time, the very first check included.

Every source was read strictly one after another, so the wait was all of them
added together. Craigslist runs on its own servers and shares nothing with the
other sites, so it is now read alongside the rest instead of ahead of them, and
a check is shorter by about as long as Craigslist takes.

No site is asked for anything more than it was. Each is still read one page at
a time, and every other source is read in the same order and at the same pace
as before. Where the app decides by the clock how much to read -- whether a
source still fits in the time limit, how many listings to open, how many older
homes to look in on -- each source is still given only the time it would have
had waiting its turn behind Craigslist, so being reached sooner never means
asking for more.

If this ever turns out to cost something, SF_HOUSING_SEQUENTIAL_SCAN=1 puts
every source back in one line exactly as it was.

SF Home Finder 0.5.3

Upgrading on Windows could fail part way through. The installer asked the
running app to stop, waited two seconds and began replacing its files, and
Windows will not delete a file that is still open. Two seconds is usually
enough, which is the worst kind of usually: the machines where shutting down
takes longer are the slow ones and the busy ones, which are the same machines
where a failed upgrade is hardest to recover from. Repair went through the
same path and could fail the same way.

It now waits for the old copy to actually let go, insists after ten seconds,
and retries each replacement, because antivirus and the search indexer can
hold a file open for a moment after the process that owned it is gone.

Nothing changes on a Mac.

SF Home Finder 0.5.2

Windows is a real download again. The last one was 0.3.9, eleven releases
ago, and the installer in it had been looking for a file that stopped being
built long before that, so anybody who tried it got an error and no app.

It is not fixed by having been read this time. Every change now builds the
Windows release on a Windows machine, installs it the way you would, waits
for the dashboard, asks it what a real deal would shortlist and then
uninstalls it again. Three faults turned up doing that, all of which a
Windows user would have hit: the installer gave up waiting after 45
seconds, which macOS learned in 0.4.2 was too short for a first start;
uninstalling could not delete the app while it was still shutting down and
stopped half way with a permission error; and opening the browser at the
very end could fail an install that had entirely worked.

If you are on a Mac, one thing changed for you. When a newer version
exists the note in the footer told everyone to run a terminal command,
including the people on Windows, where no such command exists. It now says
whichever is true where you are reading it.

The download page says which machines this runs on before it says how to
install it, rather than mentioning it in small print underneath, and says
plainly that Intel Macs are not supported yet.

SF Home Finder 0.5.1

It can tell you when there is a newer version, and fetch it for you.

Until now there was no way for a fix to reach anyone. If something was wrong
with the copy on your Mac, it stayed wrong, because nothing here reports
anything and the only way to learn a fix existed was to go back to the download
page and look. Type homefinder update and it takes you to the newest version,
keeping your homes, your deal and your notes.

When a newer version exists, one line says so: in the terminal after you type
homefinder, and in small print at the bottom of the app for anybody who does
not use the terminal. It never interrupts and there is nothing to dismiss.

This means the app now makes one request of its own. Once a day it asks GitHub
whether a newer version has been released, which is the same public page anyone
can open in a browser. It sends nothing: no search, no identifier, not even
which version you are running, because the comparison happens on your Mac after
the answer comes back. If you would rather it never asked, set
SF_HOUSING_NO_UPDATE_CHECK=1 and it never will.

Your Mac will not wait on any of this. The question is asked in the background
on a schedule, the answer is kept on disk, and every page reads what was kept,
so the app is exactly as quick offline as on.

SF Home Finder 0.5.0

The number beside the match slider is right now, in three places it was wrong.

Raising your budget could not raise it. Whatever you typed, the number stopped
at whatever your saved budget already allowed, so asking for more money looked
like it found nothing. It was counting only the homes your last saved deal had
already accepted, which left out every home the old budget had priced out. It
now counts against the deal you are writing, and on a real board that is the
difference between 423 homes and more than 1,300.

People splitting a home were shown a small fraction of what is out there. The
form asks what each person pays, and the estimate was reading that as the rent
for the whole flat: a couple at $2,700 each was priced as though one of them
were renting a two-bedroom alone. They can pay $5,400 between them. They were
told about five homes where there were closer to three hundred.

Naming neighborhoods made no difference to the estimate. Picking one area and
picking eight gave the same number, because it was counting the three
priority lists rather than the places in them.

Everything above is checked against a real board of 6,935 homes, one deal at a
time. The estimate still comes in under what is actually there, which is the
way round it should be wrong.

SF Home Finder 0.4.9

The homefinder command handles being wrong about the world. If the app is not
installed on the machine, every command now says so and gives you the line to
install it, instead of telling you it "may still be starting" and leaving you
waiting for something that was never coming. Mistyping the number of lines for
homefinder logs gets a sentence about what to type rather than one about tail.
Problems are reported on the error stream, so piping or logging still shows
them.

It runs under the bash macOS itself ships, which is what an older Mac has.

SF Home Finder 0.4.8

While you are writing your deal, the match slider now tells you roughly how
many homes a search like yours usually finds, instead of waiting for the first
search to say anything. Widen your budget or add a neighborhood and the number
moves as you type.

It is an estimate and says so: it reads "about 190 homes" rather than a count,
because nothing has been searched yet. The figures behind it were measured from
a real board of 6,935 San Francisco homes -- what each size of home rents for,
how many of each the sources carry -- and they are pitched low on purpose. The
first real search usually finds more than the estimate promised.

SF Home Finder 0.4.7

Two things somebody found installing this on a Mac that was not mine.

The homefinder command could not be found. The installer told you to add a line
to ~/.zshrc, which is the wrong file if your shell is bash, and a step that is
printed rather than performed is a step almost nobody performs. It now adds the
line itself, to whichever file your own shell reads, once, and tells you to
open a new Terminal window.

And while you were still filling in your deal, the match slider read "0 homes",
because nothing had been searched yet. That looks like a verdict on your
answers when it only means the first search has not run. The number now waits
until there is something to count.

SF Home Finder 0.4.5

The isolated install and uninstall used for testing no longer reach into the
copy you actually use. ~/.local/bin is shared by every install on a machine, so
a throwaway one writing the homefinder command there -- or a throwaway
uninstall removing it -- took the command belonging to the real installation.
Isolated runs keep their command inside their own folder now, which is the rule
the login service has always followed.

Nothing to do if you only ever installed this the normal way.

SF Home Finder 0.4.4

The terminal command is homefinder. It shipped in 0.4.3 as housefinder, which
is not what the app is called and never was; upgrading removes the old name so
you are not left with two commands, one of them wrong.

Typing homefinder opens your dashboard, and that is all most people will ever
need it for. Everything else -- status, check, logs, restart, repair,
uninstall -- is behind homefinder help rather than in your way.

SF Home Finder 0.4.3

There is a terminal command now. Type homefinder to open the dashboard, or
homefinder status, check, logs, restart, repair and uninstall for the rest. It
goes in ~/.local/bin, so it still needs no password, and the installer says so
if that folder is not on your PATH rather than leaving you with a command that
cannot be found.

It matters most if you installed with the one-line command, since that leaves
you no folder of shortcuts -- until now the bookmark was the only way back in.

SF Home Finder 0.4.2

Installing no longer reports failure when it worked. A first start on a full
board spends about fifteen seconds re-ranking what is already stored, and macOS
waits ten seconds between restarts of a background service, so a normal install
could take longer than the old 45-second window and be told "installation
stopped" for an app that was seconds from answering. It now waits properly, and
if it still has not answered it says what is actually true -- installed, still
starting, here is the address -- instead of sending you to Repair.

The installer also says less. Fifty-one package names scrolled past on every
install; now it tells you what it is doing and stays quiet about the rest. When
it finishes it tells you the address to bookmark, which matters if you
installed with the one-line command and so have no folder of shortcuts.

SF Home Finder 0.4.1

Renamed. The app called itself SF Home Finder while everything around it said
SF Housing Monitor, so people downloaded one name and were greeted by another.
The app, the download, the installer and every command file now agree.

Your existing installation is unaffected and nothing needs reinstalling twice:
the folder your profile and listings live in, and the login service that runs
the checks, deliberately keep their old names. Renaming those would have
orphaned the history of everyone who already had it, which is a poor trade for
a tidier path.

SF Home Finder 0.4.0

Homes that have been taken down now leave the shortlist promptly. The app has
always gone and read the page rather than guessing from a listing's absence,
but it was only managing a few of those checks per scan against a backlog of
ninety, so a post could be flagged and pulled and still sit there looking live
for two days. It now gets through about twenty a scan, and nothing is ever
marked gone on a failed request, a timeout or a block -- only on the page
itself saying so.

Checking for new homes by hand is now limited to once a day. The scheduled
checks, the nightly sweep and the catch-up after a sleeping Mac are unchanged
and never refused; the limit is on the button, which previously had none, and
it is there so that pressing it repeatedly cannot get a source to stop
answering. Refusing tells you when the app next checks on its own.

While you are editing your deal, the number beside the match slider now follows
what you have typed rather than what was last saved, so changing a budget or an
area shows what it would actually cost you straight away.

The login-service check no longer reports the service missing on a Mac where it
is installed and running, which could happen when a location variable was set
but left empty.

SF Home Finder 0.3.7
========================

Release scope
-------------

This is the local build. It starts blank, runs only on this Mac, and keeps the profile, listings, decisions, connector tokens, and logs under the user's Library/Application Support folder.

The included Verify command opens a local Ready Check that validates the runtime, private storage, SQLite integrity/schema, deal activation, scan/source state, optional connectors, and login service. Its copyable report redacts credentials and personal paths.

This release adds one actionable Ready Check/Repair Doctor and makes Gmail a provider-level, exact-scope alert connector for Zillow, HotPads, Apartments.com, Zumper, Roomies, and supported Facebook Marketplace alert mail. Gmail remains optional and never blocks public-source first value.

It also adds a source freshness watchdog. Craigslist, SpareRoom, and every active Gmail-backed provider retain their own durable source history. A successful zero-result check stays "Working, no matches"; parser/network failures, stale results, and repeated-failure cooldowns are shown with one next step while last-known-good listings remain available. Gmail Marketplace alerts and the optional Apify Marketplace fallback are reported as separate providers.

The isolated Verify/Repair path now explicitly carries its local no-LaunchAgent test mode through both Verify and Open into the temporary service, so clean-install diagnostics distinguish an intentionally unregistered test service from a real missing login service. The user-facing Open, Verify, Repair, and Uninstall commands now consistently hand their chosen app root to those tools too, which makes recovery behavior deterministic and safely testable. Install and Open now recognize the monitor's current healthy `/health` response, so an already-running monitor is never mistaken for an unrelated process on port 8000.

The first-run deal form is blank, uses plain neighborhood dropdowns with every SF neighborhood and a five-area cap per priority tier, and gives immediate Save/rerank feedback. The dashboard preserves a short progress or completion view even when a source check finishes too quickly to otherwise be seen.

Verified for this artifact
--------------------------

- macOS 15.6.1 on Apple Silicon (arm64)
- clean installation without sudo, Homebrew, Git, or a preinstalled Python
- a home folder path containing spaces
- blank onboarding, canonical deal creation, live Craigslist collection, classification, ranking, SQLite persistence, and rendered shortlist/near-match recovery
- honest live zero-inventory states for Listings Project and Abacus
- open, save, note, restart, Repair, uninstall-with-data-preservation, and reinstall recovery
- occupied-port refusal without stopping the other app
- generated LaunchAgent plist syntax and dynamic paths
- release checksum, bundled-file checksums, private-path scan, and personal-data exclusion

Important limitations
---------------------

- This unsigned build may require Control-click, Open the first time.
- Intel Macs are not supported by this ZIP.
- The generated login LaunchAgent was syntax-checked but was not loaded into the builder's real login domain during automated validation. Install/Repair report a clear error if macOS rejects it.
- The release does not contain an owner Google OAuth client. Gmail email-alert coverage therefore shows Owner setup required until the owner supplies that client. No Gmail token is bundled.
- Gmail authorization, Apify/Facebook, and the Furnished Finder Chrome bridge have fixture/failure-path coverage but were not live-authorized with owner credentials in this build.
- Furnished Finder requires Chrome's manual Load unpacked step. Chrome does not allow this local unsigned extension to install itself silently.
- A first-time usability test by an uninvolved nontechnical person still has to be completed before calling the build fully production-ready.
